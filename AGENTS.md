# AGENTS.md

Guide for AI agents working in this repo: ESPHome device configs that are
controlled from Home Assistant (HA).

## Repo layout

- One device per file: `<device>.yaml` holds the ESPHome config and
  `<device>.md` holds short notes (pinout, links, states, HA examples).
  - `alarm.yaml` / `alarm.md`: ESP32-S3 DevKitC-1, onboard RGB LED on GPIO48
    that shows the alarm state.
  - `wallclock.yaml` / `wallclock.md`: ESP32-C3 supermini, MAX7219 clock.
  - `weather.yaml` / `weather.md`: ESP32-C3, deep-sleep weather sensor.
- `fonts/`: fonts for displays.
- `secrets.yaml`: Wi-Fi credentials, referenced as `!secret wifi_ssid`.
  Git ignores it. Never print it or commit it.
- `.esphome/` and `.device-builder*` are generated by ESPHome Device Builder.
  Git ignores them. Don't edit them.

## Rules

- Never commit or push unless the user asks.
- Keep the header comment (`# Board: ...`, `# Definition: ...`) at the top of
  each yaml file.
- When a device's behaviour changes, update its `.md` file too.
- If you rename an entity (`name:`), tell the user: the HA entity ID changes
  too, and HA automations that use the old ID stop working.

## Validate before you report done

ESPHome is not installed system-wide. Use a temporary virtualenv:

```bash
python3 -m venv /tmp/esphome-venv
/tmp/esphome-venv/bin/pip install -q esphome
/tmp/esphome-venv/bin/esphome config  <device>.yaml   # schema check
/tmp/esphome-venv/bin/esphome compile <device>.yaml   # catches C++/lambda errors
```

- `config` alone misses lambda errors. Always run `compile` too.
- The first ESP-IDF compile downloads the toolchain into `~/.cache/esphome`
  and takes several minutes. Use a long timeout.
- Flashing (`esphome run <device>.yaml`) and testing on hardware are up to the
  user unless they ask you to do it. State clearly what you did not test on
  the device.

## ESPHome patterns used here

### HA-driven state: template select -> device logic

To let HA set a mode (for example the alarm level), expose a template
`select`. HA automations set the option, and the device maps each option to
hardware actions:

```yaml
select:
  - platform: template
    name: "Alarm State"           # HA entity: select.<device>_alarm_state
    id: alarm_state
    optimistic: true
    options: ["Off", "None", "Yellow", "Red"]
    initial_option: "Off"
    restore_value: false          # true = restore last option from flash
    on_value:
      then:
        - if:
            condition:
              lambda: 'return x == "Red";'   # x = selected option string
            then:
              - light.turn_on: { id: my_light, effect: "Red Strobe" }
```

- Quote `"Off"`, `"On"`, `"Yes"` and `"No"`. Unquoted, YAML reads them as
  booleans.
- In `on_value`, `x` is the option string and `i` is its index.

### Light effects and state

Reference: https://esphome.io/components/light/

- Set the color, brightness and effect in one `light.turn_on` call. `pulse`
  fades whatever color is currently set, so setting the color in the same
  call is how you get an amber pulse.
- `effect: none` stops a running effect when you go back to a steady color.
- `pulse`: one period is about 2 × `update_interval` when
  `transition_length` equals `update_interval`. Use `min_brightness` and
  `max_brightness` to set the range.
- `strobe`: a list of `colors`, each with its own `duration`. Use
  `state: false` for an off step.
- `restore_mode: ALWAYS_OFF` makes the LED boot dark. Pair it with
  `restore_value: false` and an `"Off"` initial option on the select, so HA
  and the LED agree after a reboot.
- ESP32-S3 DevKitC-1 onboard LED: `platform: i2s_clockless_led_strip`,
  `pin: GPIO48`, `channel_colors: GRB`, `num_leds: 1`.

### Logging

```yaml
- logger.log:
    format: "Alarm state -> %s"
    args: ["x.c_str()"]
```

## Home Assistant side

- Entity IDs are `<domain>.<esphome name>_<entity name, snake_case>`, for
  example `select.alarm_alarm_state` and `light.alarm_alarm_led`.
- Set a template select from an automation:

  ```yaml
  - action: select.select_option
    target:
      entity_id: select.alarm_alarm_state
    data:
      option: Red
  ```

- To test by hand, go to Developer Tools -> Actions -> `select.select_option`.
- Put HA automation examples in the device's `.md` file. This repo does not
  contain the HA config.

### Where HA automations live

The user keeps device automations in dedicated HA package files, one per
device, for example `/config/packages/alarm_led.yaml`:

```yaml
# configuration.yaml (once; a restart is needed after adding it)
homeassistant:
  packages: !include_dir_named packages
```

```yaml
# /config/packages/<name>.yaml
automation:
  - id: <unique_id>          # needed for traces
    alias: ...
```

- Automations from packages are read-only in the HA UI; edit the file.
- After an edit: Developer Tools -> YAML -> Check configuration, then reload
  Automations.
- If packages are not used: `automation manual: !include_dir_merge_list
  automations/`. The file is then a bare list (`- id: ...`) without the
  `automation:` key.
- Use the current syntax: `triggers:` / `trigger:`, `conditions:`,
  `actions:` / `action:`. Use `to: null` on a state trigger to fire on state
  changes only, ignoring attribute updates.
- Prefer device-side state (next section) when the ESP must show HA state
  after a reboot. An HA automation triggered `from: unavailable` misses
  quick reboots that HA never sees as a disconnect.

### ESP reads HA state (preferred for "show HA state" devices)

Use a `homeassistant` text_sensor on the ESP and map it there. HA pushes the
current value on every API connect, so the device re-syncs by itself after a
reboot or Wi-Fi drop, with no HA automation:

```yaml
text_sensor:
  - platform: homeassistant
    id: uap_air_alert_level
    entity_id: sensor.uap_31_air_alert_level
    internal: true
    on_value:
      then:
        - select.set:
            id: alarm_state
            option: !lambda |-
              if (x == "none") return "None";
              ...
              return "Off";   // unknown / unavailable
```

### Ukraine Alarm Pro integration (alarm source)

- HACS integration: https://github.com/ABovsh/ukraine-alarm-pro. It is
  already configured in the user's HA for region `31`.
- A HACS page URL like `http://homeassistant.local/.../repository/<number>`
  contains the GitHub repo ID. Resolve it with
  `curl -s https://api.github.com/repositories/<number>`.
- The alarm LED uses `sensor.uap_31_air_alert_level`, which has the states
  `none`, `yellow`, `red` and `unrecognized`. Mapping: none -> None,
  yellow -> Yellow, red and unrecognized -> Red, unknown/unavailable -> Off.
  The mapping lives in `alarm.yaml` (`text_sensor` `uap_air_alert_level`);
  there is no HA automation for it.
- Other entities you can add on request:
  - `binary_sensor.uap_31_alert`: any threat, including non-air threats
    such as artillery, which leave the level sensor at `none`.
  - `binary_sensor.uap_data_stale`: no data for 15 min. The level sensor
    keeps its last value in that case.
- Test without a real alert: Developer Tools -> States -> set the sensor
  value temporarily. The integration overwrites it on its next update.

### Checking HA automations locally

HA is not installed here. Before you hand over an automation:
- Parse it with `python3 -c "import yaml; ..."`.
- Render its Jinja templates with `jinja2`, replacing `states()` and
  `is_state()` with stubs, for every possible source state.
- Tell the user it has not been run in HA.
